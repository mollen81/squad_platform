# event-service

Сервис клановых ивентов Squad: создание ивента, набор участников, формирование составов
на каждую игру, запуск и завершение игр, сбор статистики. Общается с платформой по gRPC
(входящие вызовы от API-гейтвея) и по Kafka (исходящие события + входящие сообщения о
сервере от vps-сервиса).

Написан на Go, данные — в общей Postgres платформы, схема разворачивается миграцией.

## Что делает сервис и чего не делает

**Делает:**

- ведёт ивент от создания до завершения, включая автоматические переходы по времени;
- набирает участников и следит за сторонами (своя сторона / сторона противника);
- формирует составы команд на каждую запланированную игру;
- заказывает игровой сервер (сообщением в Kafka) и принимает от vps-сервиса факты покупки
  и деплоя;
- открывает запуск ивента по готовности сервера и подтверждению обоих сайд-лидеров;
- ведёт игры: старт, финиш, победитель, счёт серии, статистика игроков и суммы по команде;
- публикует все значимые изменения в Kafka.

**Не делает (и не должно):**

- **не проверяет подлинность пользователя.** `user_id` во всех запросах приходит из
  API-гейтвея, который уже проверил токен. Сервис доверяет этому полю и проверяет только
  принадлежность к ивенту и роль (сайд-лидер он или нет);
- не покупает и не настраивает сервер — это vps-сервис;
- не хранит профили игроков и клановую иерархию — это user-service;
- не считает рейтинги и агрегаты по игрокам — это stats-service, он читает наши события.

## Быстрый старт

### Через docker compose (как в платформе)

Из корня репозитория:

```bash
docker compose up -d --build event-service
```

Compose сам поднимет зависимости и накатит миграцию: сервис `event-service` ждёт
`postgres`, `kafka`, `kafka-init` (создаёт топики `event-service` и `vps-service`) и
`migrate-event` (применяет `migrations/`).

### Локально, без контейнера

```bash
export POSTGRES_HOST=localhost POSTGRES_PORT=5433 POSTGRES_USER=admin POSTGRES_DB=main_db
export POSTGRES_PASSWORD=...                      # обязательно, дефолта нет
export SPRING_KAFKA_BOOTSTRAP_SERVERS=localhost:9092
export EVENT_SERVICE_GRPC_PORT=9096

make build && ./bin/event-service
```

Миграцию в этом случае накатить руками:

```bash
docker exec -i squad_postgres psql -U admin -d main_db < migrations/000001_init.up.sql
```

### Если схема уже накатана, а миграция изменилась

Пока сервис не в проде, миграция одна и правится на месте. `golang-migrate` не
перезапускает уже применённую версию, поэтому на базе, где схема есть, новые колонки сами
не появятся — `migrate-event` скажет «no change». Одноразовый сброс:

```bash
make db-reset                                       # удалит таблицы event-service и запись о версии
docker compose up -d migrate-event event-service    # накатит миграцию заново
```

Данные event-service при этом теряются; таблицы других сервисов не затрагиваются. Когда
выйдем в прод, вместо сброса появится `000002` и далее по порядку.

### Проверка, что живой

Сервис включает gRPC reflection, поэтому `grpcurl` работает без `.proto`:

```bash
grpcurl -plaintext localhost:9096 list event.EventService
grpcurl -plaintext -d '{"user_create_id":"<uuid>"}' \
  localhost:9096 event.EventService/GetEventsByCreatorId
```

### Makefile

| Цель | Что делает |
|---|---|
| `make proto` | перегенерирует `event.pb.go` и `event_grpc.pb.go` из `event.proto` (нужны `protoc`, `protoc-gen-go`, `protoc-gen-go-grpc`) |
| `make build` | собирает бинарник в `bin/event-service` |
| `make run` | собирает и запускает |
| `make clean` | удаляет `bin/` |
| `make db-reset` | удаляет таблицы event-service и запись о версии миграции, чтобы `000001` накатился заново (см. выше) |

## Конфигурация

Всё через переменные окружения, все имена совпадают с тем, что уже используется в
`docker-compose.yml` платформы.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSTGRES_HOST` | `localhost` | хост Postgres |
| `POSTGRES_PORT` | `5432` | порт Postgres |
| `POSTGRES_USER` | `admin` | пользователь |
| `POSTGRES_PASSWORD` | **нет** | пароль; без него сервис падает на старте с `POSTGRES_PASSWORD is not set` |
| `POSTGRES_DB` | `main_db` | база |
| `SPRING_KAFKA_BOOTSTRAP_SERVERS` | `localhost:9092` | брокер Kafka (имя переменной унаследовано от Java-сервисов платформы) |
| `KAFKA_TOPIC` | `event-service` | топик, **в который сервис пишет** свои события |
| `KAFKA_VPS_TOPIC` | `vps-service` | топик, **из которого сервис читает** сообщения vps-сервиса |
| `KAFKA_VPS_GROUP_ID` | `event-service` | consumer group для чтения топика vps-сервиса |
| `EVENT_SERVICE_GRPC_PORT` | `9096` | порт gRPC-сервера |

Пароль намеренно без дефолта: значение в коде попадает в репозиторий. Держите его в `.env`
(файл в `.gitignore`) или в секретах окружения.

Топики должны существовать заранее. В `Writer` включён `AllowAutoTopicCreation`, но на
брокере платформы автосоздание выключено, поэтому топики создаёт `kafka-init` в compose.

## Архитектура

```
cmd/main.go                        точка входа: конфиг, пул Postgres, Kafka, сборка слоёв,
                                   RecoverPendingEvents, gRPC-сервер, graceful shutdown

internal/core/
  domain/         domain.go        сущности (Event, User, Team, TeamMember), статусы, роли,
                                   бизнес-константы времени, методы-предикаты на сущностях
                  errors.go        доменная ошибка с категорией (Kind) — из неё транспорт
                                   выбирает gRPC-код
  kafka/          producer.go      Writer: публикация событий (реализация EventProducer)
                  consumer.go      Reader: чтение топика vps-сервиса, коммиты и повторы
  proto/          event.proto      контракт gRPC + сгенерированные *.pb.go

internal/layers/
  service/        port.go          интерфейсы: EventService (что сервис предоставляет),
                                   EventRepository и EventProducer (что ему нужно)
                  service.go       вся бизнес-логика, таймеры, транзакционные сценарии
                  validate.go      проверки входных данных
                  event_lock.go    мьютекс на каждый event_id
  repository/     postgres.go      SQL, транзакции (WithTx), маппинг строк в домен
  transport/      grpc.go          gRPC-хендлеры
                  kafka.go         разбор сообщений vps-сервиса и вызов сервиса
                  status.go        доменная категория ошибки -> gRPC-код
                  mapper.go        домен -> protobuf

migrations/                        схема БД (golang-migrate)
e2e_test.sh                        сквозной сценарий через grpcurl
```

### Направления зависимостей

Это главное, что стоит понять перед правками:

```
transport/grpc.go  ──┐
transport/kafka.go ──┼──►  service  ──►  EventRepository  ──►  repository/postgres.go
                     │                └─►  EventProducer   ──►  core/kafka/producer.go
core/kafka/consumer.go (Reader) ──► отдаёт байты в transport/kafka.go
```

- **Пакет `service` не знает ни про Kafka, ни про gRPC, ни про формат сообщений.** Его
  собственные импорты — стандартная библиотека, `domain` и `uuid`, и ничего больше
  (`encoding/json` виден в `go list -deps` только транзитивно, через `uuid`). Именно поэтому
  юнит-тесты гоняются без брокера и без базы.
- **Продюсер — исходящая зависимость.** Сервис его вызывает, поэтому интерфейс
  `EventProducer` объявлен рядом с сервисом (`port.go`), а реализация живёт в
  `core/kafka/producer.go` и подставляется в `main.go`.
- **Консьюмер — входящий транспорт**, такой же как gRPC-хендлер: его никто в сервисе не
  вызывает, он сам вызывает сервис. Поэтому разбор сообщения лежит в
  `transport/kafka.go`, а чтение из брокера — в `core/kafka/consumer.go`, симметрично
  продюсеру.

Если добавляете новый источник вызовов (HTTP, ещё один топик) — он идёт в `transport`, а
методы сервиса при необходимости добавляются в `EventService`.

## Модель данных

Четыре таблицы, все в общей базе платформы. Схема — `migrations/000001_init.up.sql`.

### `events`

| Колонка | Смысл |
|---|---|
| `event_id` | PK |
| `name` | название (обрезается по краям, максимум 100 символов) |
| `user_create_id` | внешний `user_id` создателя, он же сайд-лидер «своей» стороны |
| `enemy_side_leader_id` | внешний `user_id` сайд-лидера стороны противника |
| `time_start` | заявленное время старта, от него считаются контрольная точка и аренда |
| `time_finish` | NULL, пока ивент не завершён |
| `user_count` | денормализованный счётчик участников, поддерживается в той же транзакции, что вставка/удаление в `users` |
| `target_game_count` | сколько игр запланировано, 1–3 |
| `game_count` | сколько игр уже закрыто |
| `status` | см. [жизненный цикл](#жизненный-цикл-ивента) |
| `winner_side` | `''` пока не решено, затем `ally` / `enemy` / `draw` |
| `rent_server_sent` | сигнал об аренде сервера уже отправлен (чтобы после рестарта не отправить второй раз) |
| `server_ip` | адрес сервера строкой (`TEXT`, не UUID: формат задаёт vps-сервис — IPv4, IPv6, возможно с портом), приходит в `vps.purchased` |
| `server_password` | пароль к серверу, оттуда же |
| `server_deployed_at` | момент получения `vps.deployed` **по часам сервиса** |
| `ally_ready_at`, `enemy_ready_at` | когда сайд-лидер соответствующей стороны нажал `StartEvent` |

### `users` — участие человека в ивенте

| Колонка | Смысл |
|---|---|
| `user_event_id` | PK, **внутренний** id участия |
| `user_id` | внешний id из сервиса авторизации |
| `event_id` | ивент |
| `clan_id` | клан, с которым человек пришёл |
| `enemy` | сторона: `false` — сторона создателя, `true` — сторона противника |
| `join_time` | когда вошёл |

Уникальность `(event_id, user_id)` — один человек не может войти в ивент дважды.

**Ключевой момент:** в API наружу всегда ходит внешний `user_id`, а внутри всё
связывается через `user_event_id`. Сервис сам резолвит одно в другое. Роли у участия
нет — она есть только в составе команды (см. ниже).

### `team` — участие одной стороны в одной игре

Отдельной таблицы «игра» нет. Одна игра — это **две строки** в `team` с одинаковым
`game_number`, различающиеся `side_leader_id`. То есть `team` это не «команда клана», а
«сторона в конкретной игре».

| Колонка | Смысл |
|---|---|
| `team_id` | PK |
| `event_id` | ивент |
| `game_number` | номер игры внутри ивента (1..`target_game_count`) |
| `side_leader_id` | ссылка на `users.user_event_id` сайд-лидера этой стороны — по нему определяется сторона команды |
| `status` | `pending` / `in_progress` / `finished` |
| `winner` | выставляется при закрытии игры |
| `members_count` | счётчик состава, поддерживается транзакционно |
| `time_start`, `time_finish` | NULL, пока не началась / не закончилась |
| `total_*` | суммы по составу, пересчитываются при каждом `AddTeamMemberStats` |

Уникальность `(event_id, game_number, side_leader_id)`: на игру по одной строке на сторону.

### `team_members` — состав команды

| Колонка | Смысл |
|---|---|
| `team_id`, `user_event_id` | составной PK |
| `role` | `player` / `squad_leader` / `side_leader` — роль **в этой игре** |
| `kills`, `deaths`, `points`, `revival`, `destroyed_vehicles` | статистика за игру |
| `six_clan_members` | сигнал другому сервису, звать ли игрока в игру |

**`six_clan_members`** считается по клану **внутри команды**, а не по всему ивенту: если в
этой команде набралось 6 и больше человек одного клана, флаг ставится всей группе сразу
(не только тому, кто перевалил порог). Когда кто-то уходит и однокланников остаётся меньше
шести, флаг снимается со всей группы. Порог задан в двух местах и должен совпадать:
`CheckSixClanMembers` в репозитории считает 5 «других» участников, `refreshSixClanMembers`
в сервисе проверяет «меньше 6 всего».

## Жизненный цикл ивента

```
                 набрался минимум          vps.purchased        vps.deployed
pending ─────────────────────────► confirmed ──────────► purchased ──────────► deployed
   │                                   │                     │                    │
   │ не набрался                       │                     │                    │ +15 мин
   ▼                                   │                     │                    ▼
declined                               │                     │                  ready
                                       │                     │                    │
                                       └──── отмена ─────────┴────────┬───────────┤ оба нажали
                                                                      ▼           │ StartEvent
                                                                  canceled        ▼
                                                                             in_progress
                                                                                  │ сыграны все игры
                                                                                  │ или решена серия
                                                                                  ▼
                                                                              finished
```

| Статус | Что означает | Что в нём можно |
|---|---|---|
| `pending` | ивент создан, идёт набор | входить и выходить, менять время, отменять, собирать составы |
| `confirmed` | к контрольной точке набрался минимум игроков | состав ивента **заморожен**; составы команд ещё можно менять; ждём сервер |
| `purchased` | vps-сервис доложил о покупке сервера | доступен `GetServerData` |
| `deployed` | vps-сервис доложил о деплое | идёт отсчёт 15 минут до открытия `StartEvent` |
| `ready` | сервер выждал `ServerReadyDelay` | сайд-лидеры могут звать `StartEvent` |
| `in_progress` | ивент стартовал, идут игры | `StartTeamGame`, `FinishTeamGame`, `AddTeamMemberStats` |
| `finished` | все игры сыграны или серия решена досрочно | только чтение |
| `declined` | к контрольной точке не набралось игроков | только чтение |
| `canceled` | отменён создателем или автоматически | только чтение |

### Кто двигает статусы

| Переход | Чем вызывается |
|---|---|
| `pending → confirmed` | таймер контрольной точки (`time_start − 30 мин`), если `user_count >= 80` |
| `pending → declined` | тот же таймер, если игроков меньше |
| `pending/confirmed/purchased/deployed/ready → canceled` | `CancelEvent` создателем, либо автоотмена (нет сервера, никто не нажал `StartEvent`) |
| `confirmed → purchased` | сообщение `vps.purchased` |
| `purchased → deployed` | сообщение `vps.deployed` |
| `deployed → ready` | таймер, через `ServerReadyDelay` после получения `vps.deployed` |
| `ready → in_progress` | `StartEvent` от обоих сайд-лидеров, либо автостарт по `StartVoteTimeout` |
| `in_progress → finished` | `FinishTeamGame`, когда серия решена |

Переходы защищены на уровне SQL: `UpdateEventStatus` меняет статус только из ожидаемого
предыдущего (`WHERE status = ANY(...)`), и если не затронуло ни одной строки — возвращает
ошибку, а не тихо проходит. Поэтому повторный или опоздавший вызов не может откатить ивент
назад.

## Таймеры и восстановление после рестарта

### Константы

| Константа | Значение | Где | Смысл |
|---|---|---|---|
| `MinPlayersRequired` | 80 | `service.go` | минимум участников на контрольной точке |
| `CheckTimeBeforeStart` | 30 мин | `service.go` | за сколько до `time_start` проверяется минимум |
| `RentServerTimeBeforeStart` | 15 мин | `service.go` | за сколько до `time_start` публикуется `server.rent` |
| `MaxTeamMembers` | 50 | `service.go` | максимум состава одной команды |
| `ServerReadyDelay` | 15 мин | `domain.go` | от получения `vps.deployed` до открытия `StartEvent` |
| `StartVoteTimeout` | 15 мин | `domain.go` | сколько ждать второго сайд-лидера |
| `ServerDeployTimeout` | 30 мин | `domain.go` | сколько после `time_start` ждать так и не задеплоенный сервер |
| `publishTimeout` | 30 сек | `service.go` | предел ожидания Kafka при публикации после коммита |

### Цепочки

На каждый активный ивент — **одна** цепочка таймеров в одной горутине, зарегистрированная
в мапе `eventTimers` под мьютексом. Повторная постановка отменяет предыдущую цепочку
(так работает перенос времени), `CancelEvent` гасит её целиком.

1. **Контроль**: ждём `time_start − 30 мин` → `checkMinPlayers` → `confirmed` или
   `declined`. Если подтвердили, та же горутина продолжает:
2. **Аренда**: ждём `time_start − 15 мин` → публикуем `server.rent` со списком игроков,
   ставим флаг `rent_server_sent` **после успешной публикации**.
3. **Ожидание сервера**: ждём `time_start + 30 мин`. Если к этому моменту ивент всё ещё
   `confirmed` или `purchased` (то есть `vps.deployed` не пришло) — отменяем ивент.

Когда приходит `vps.deployed`, эта цепочка **заменяется** новой:

4. **Гейт**: ждём `server_deployed_at + 15 мин` → статус `ready`, публикуем `event.ready`.
5. **Голосование**: ждём ещё `StartVoteTimeout`. Если нажал хотя бы один сайд-лидер —
   стартуем ивент сами (сервер оплачен, срывать сбор из-за одного молчащего лидера незачем).
   Если не нажал никто — отменяем.

Каждый шаг цепочки перед работой берёт мьютекс ивента и проверяет, что цепочку не
отменили, пока он ждал.

### После рестарта процесса

`eventTimers` живёт только в памяти, поэтому `main.go` **до** старта gRPC-сервера зовёт
`RecoverPendingEvents`. Он читает все незавершённые ивенты и расставляет цепочки заново:

| Статус при старте | Что ставится |
|---|---|
| `pending` | контроль минимума игроков |
| `confirmed`, `purchased` | аренда (если ещё не отправлена) и ожидание деплоя |
| `deployed` | гейт от сохранённого `server_deployed_at` — **досиживается остаток**, а не 15 минут заново |
| `ready` | ожидание нажатий с дедлайном `start_available_at + StartVoteTimeout` |
| `in_progress` | ничего: дальше события ведут явные вызовы |

Момент, который сработал бы «в прошлом» (сервис лежал дольше, чем оставалось), не теряется:
`waitUntil` для прошедшего времени срабатывает сразу.

## Жизненный цикл игры

Игра — это пара команд с одним `game_number`. Статус игры и есть статус этих двух строк.

```
pending ──StartTeamGame──► in_progress ──FinishTeamGame──► finished
```

- **Состав и роли меняются только в `pending`.** После старта игры `JoinUserToTeam`,
  `RemoveUserFromTeam` и `SetRole` для этой команды отвечают `FailedPrecondition`.
- **`StartTeamGame`** требует: обе команды из одного ивента и одной игры, обе в `pending`,
  ивент в `in_progress`, предыдущая игра закончена. Первую игру стартует сам сервис при
  переходе ивента в `in_progress`.
- **`FinishTeamGame`** требует: обе команды в `in_progress`, победитель — одна из этих
  двух. Закрывает обе строки одним UPDATE, инкрементит `game_count` и считает серию.
- **Серия идёт до большинства побед.** При 2:0 в серии из трёх игр третья не играется:
  ивент сразу `finished`, а несыгранная пара команд остаётся в `pending` — стартовать её
  уже нельзя, потому что ивент не `in_progress`. При чётном `target_game_count` возможна
  ничья: счёт 1:1 даёт `winner_side = draw`.
- **Статистика вносится только после закрытия игры**, по одному игроку за раз. Повторный
  вызов на того же игрока **перезаписывает** его числа (это способ исправить опечатку), а
  `total_*` команды каждый раз пересчитываются как сумма по составу — не прибавляются
  дельтой, иначе повтор задваивал бы итог.

## gRPC API

Пакет `event`, сервис `EventService`, 22 метода. Ошибки отдаются **gRPC-статусами**; полей
`error` в ответах нет (они зарезервированы в proto как удалённые).

### Ивент

| Метод | Запрос | Кто зовёт | Заметки |
|---|---|---|---|
| `CreateEvent` | `user_creator_id`, `creator_clan_id`, `enemy_side_leader_id`, `enemy_side_leader_clan_id`, `event_name`, `time_start`, `target_game_count` | создатель | создаёт ивент, оба сайд-лидера и все команды на все игры одной транзакцией; старт не раньше чем через 45 минут и не позже чем через 45 дней |
| `UpdateTimeEvent` | `event_id`, `user_create_id`, `new_time_start` | создатель | только в `pending`; переставляет цепочку таймеров |

### Составы и игры

| Метод | Запрос | Заметки |
|---|---|---|
| `JoinUserToTeam` | `team_id`, `user_id`, `role` | только своя сторона, только `pending`-игра, максимум 50 в команде, роль `player` или `side_leader` |
| `RemoveUserFromTeam` | `team_id`, `user_id` | только `pending`-игра; сайд-лидера убрать нельзя |
| `SetRole` | `team_id`, `side_leader_id`, `user_id`, `role` | роль действует **в одной игре**; звать может только сайд-лидер этой же команды |

### Коды ошибок

Сервисный слой размечает ошибки категориями (`domain.ErrorKind`), транспорт переводит их в
канонические коды gRPC:

| Ситуация | Код | № |
|---|---|---|
| невалидный или пустой uuid, пустое название, отрицательная статистика, недопустимая роль | `InvalidArgument` | 3 |
| нет ивента, команды, участника | `NotFound` | 5 |
| повторный вход в ивент или команду | `AlreadyExists` | 6 |
| не создатель, не тот сайд-лидер, попытка выхода сайд-лидера | `PermissionDenied` | 7 |
| не тот статус, игра уже началась, состав заполнен | `FailedPrecondition` | 9 |
| конфликт транзакций не разошёлся за 5 попыток | `Aborted` | 10 |
| база недоступна | `Unavailable` | 14 |
| клиент оборвал запрос / вышел дедлайн | `Canceled` / `DeadlineExceeded` | 1 / 4 |
| всё остальное | `Internal` | 13 |

`Aborted` и `Unavailable` означают «повтори запрос». `Internal` наружу уходит без
подробностей (текст всегда `internal error`), настоящая причина пишется в лог — так
внутренние ошибки Postgres не утекают клиенту.

Топик из `KAFKA_TOPIC` (по умолчанию `event-service`), формат — JSON с полем `type`.
Ключ сообщения — `event_id` или `team_id`, значит сообщения по одному ивенту (или одной
команде) попадают в одну партицию и сохраняют порядок.

| `type` | Ключ | Поля | Когда |
|---|---|---|---|
| `event.created` | `event_id` | `event_id`, `name`, `user_create_id`, `time_start`, `create_time` | ивент создан |
| `event.time_updated` | `event_id` | `event_id`, `user_create_id`, `new_time_start` | перенесено время |

| `event.ready` | `event_id` | `event_id`, `start_available_at` | сервер готов, `StartEvent` открыт |
| `event.side_ready` | `event_id` | `event_id`, `user_id`, `side`, `ready_at`, `both_ready` | сайд-лидер нажал `StartEvent` |
| `event.started` | `event_id` | `event_id`, `time_start` | ивент стартовал |
| `event.finished` | `event_id` | `event_id`, `winner_side`, `time_finish` | ивент завершён |
| `user.joined_event` | `event_id` | `event_id`, `user_id`, `clan_id`, `enemy`, `join_time` | игрок вошёл |
| `user.left_event` | `event_id` | `event_id`, `user_id` | игрок вышел |
| `user.joined_team` | `team_id` | `team_id`, `user_id`, `user_event_id`, `role` | игрок в составе |
| `user.left_team` | `team_id` | `team_id`, `user_id`, `user_event_id` | игрок убран из состава |
| `user.role_changed` | `event_id` | `event_id`, `team_id`, `user_id`, `role` | роль в конкретной игре изменена |

**`event.side_ready` — это и есть сигнал «противник готов».** Отдельного сообщения «нажал
именно вражеский лидер» нет: сторона определяется полем `side` (`ally` — сторона создателя,
`enemy` — вторая), а `both_ready` говорит, что ждать больше некого и ивент стартует.

## Kafka: входящие сообщения от vps-сервиса

Топик из `KAFKA_VPS_TOPIC` (по умолчанию `vps-service`), consumer group из
`KAFKA_VPS_GROUP_ID` (по умолчанию `event-service`).

```json
{"type":"vps.purchased","event_id":"<uuid>","server_ip":"<строка>","server_password":"<строка>"}
{"type":"vps.deployed","event_id":"<uuid>","server_ip":"<строка>"}
```

`event_id` vps-сервис берёт из нашего `server.rent`. **Времени в `vps.deployed` нет
намеренно**: моментом готовности считается время получения сообщения по часам
event-service, от него и отсчитываются 15 минут.

### Что проверяется

| Сообщение | Проверки |
|---|---|
| `vps.purchased` | `event_id` — валидный uuid; `server_ip` — непустая строка не длиннее 64 символов (обрезается по краям), формат не разбирается; пароль не пустой; ивент существует; статус ровно `confirmed`. Повтор того же `server_ip` — no-op. Другой `server_ip` поверх уже купленного — отказ |
| `vps.deployed` | SELECT по паре `(event_id, server_ip)` с блокировкой строки: если такой пары нет, сообщение не применяется. Статус должен быть `purchased`. Повтор не сдвигает `server_deployed_at` |

Когда пара не найдена, различаются три случая: ивента нет (`NotFound`), сервер не куплен
(`FailedPrecondition`), куплен другой сервер (`NotFound`, в тексте оба адреса) — в логе видно,
что именно не сошлось.

### Семантика консьюмера

- `StartOffset: FirstOffset` — если сервис лежал в момент покупки, сообщение будет
  прочитано, а не пропущено;
- **оффсет коммитится вручную и только после успешной обработки** (`CommitInterval: 0`);
- **временная ошибка** (`Unavailable`, `Aborted`, `Internal` — недоступна база, конфликт
  транзакций) → повтор того же сообщения с растущей паузой от 2 до 30 секунд. Очередь при
  этом задерживается, но сообщение о купленном сервере не теряется;
- **неустранимая ошибка** (битый JSON, неизвестный `type`, чужой ивент, не тот статус) →
  сообщение пропускается с записью в лог, иначе оно заблокировало бы партицию навсегда.

## Конкурентность и транзакции

Три механизма, каждый закрывает свой класс проблем.

**1. Мьютекс на каждый `event_id`** (`event_lock.go`). Все изменяющие операции над одним
ивентом — и ручки, и шаги таймеров — выполняются под ним по очереди, включая публикацию в
Kafka. Даёт две вещи: сообщения по ивенту уходят в том же порядке, в каком закоммичены
изменения, и шаг таймера не может выполниться посреди `CancelEvent`. Ожидание мьютекса
прерывается по отмене контекста, так что отвалившийся клиент не занимает очередь.
Мьютекс живёт только внутри процесса.

**2. Транзакция `SERIALIZABLE` на операцию** (`WithTx` в `postgres.go`). Первым шагом
блокируется строка ивента (`SELECT ... FOR UPDATE`, см. `lockEventRow`), и все проверки
статуса делаются уже внутри транзакции. При конфликте сериализации (40001) или дедлоке
(40P01) транзакция повторяется целиком, до 5 попыток с нарастающей паузой; если не
разошлось — клиент получает `Aborted`. Это работает и между инстансами сервиса, в отличие
от мьютекса.

Отсюда правило: **внутри `WithTx` — только работа с БД.** Побочные эффекты (Kafka,
постановка таймеров) выносятся после коммита, иначе повтор транзакции их задвоит.

**3. Защитные условия в UPDATE.** Ни один статус или счётчик не меняется «вслепую»:
переходы статусов идут с `WHERE status = ANY(...)`, старт игры — с `status = 'pending'`,
финиш — с `status = 'in_progress'`, счётчики уменьшаются только если строка реально
удалилась, `server_deployed_at` пишется только если он NULL. Число затронутых строк
проверяется, и ноль — это ошибка, а не тихий успех.

### Публикация в Kafka

Всегда **после** коммита, под тем же мьютексом, с контекстом, не зависящим от отмены
клиентского запроса (но с пределом 30 секунд). Следствие, которое надо знать: если Kafka
недоступна, изменение в БД уже сделано, а вызывающий получит ошибку. Outbox-таблицы нет —
это осознанный технический долг, см. [ограничения](#известные-ограничения).

## Валидация входных данных

Проверки живут в сервисном слое (`validate.go`), до захвата мьютекса и транзакции — чтобы
клиент получал внятную ошибку, а не `invalid input syntax for type uuid` от Postgres.

| Что | Правило |
|---|---|
| любой идентификатор | непустой и валидный UUID |
| `server_ip` | непустая строка не длиннее 64 символов, обрезается по краям; формат намеренно не проверяется — это может быть IPv4, IPv6, адрес с портом или вообще имя хоста |
| название ивента | обрезается по краям, не пустое, максимум 100 символов (считаются символы, не байты) |
| название в поиске | не пустое |
| статистика | каждый показатель `>= 0` и `<= 100000` |
| роль | только `player` или `side_leader`; `squad_leader` через API не выдаётся — он принадлежит сайд-лидеру стороны и ставится при создании ивента |
| время старта | не раньше чем через 45 минут и не позже чем через 45 дней |
| количество игр | 1, 2 или 3 |

Юнит-тесты не покрывают склейку с Kafka и реальные тайминги. Полезные сценарии для
ручного прогона на укороченной сборке: автостарт по таймауту (нажал один лидер), отмена
когда не нажал никто, отмена когда сервер не задеплоился, мусорное сообщение и неизвестный
`type` в топике, повторный `vps.deployed`, `vps.deployed` с чужим `server_ip`, и гонка —
несколько одновременных `StartEvent` от обоих лидеров (успешных нажатий должно быть ровно
два, старт один).

## Тонкие моменты

Здесь собрано то, на чём легко споткнуться.

1. **`user_id` — это доверенное поле.** Сервис не проверяет токен: считается, что API уже
   проверил. Если позвать ручку напрямую, можно представиться кем угодно.
2. **`StartTeamGame`, `FinishTeamGame` и `AddTeamMemberStats` не проверяют вызывающего
   вообще.** Кто угодно, зная `team_id`, может закрыть игру, объявить победителя и вписать
   статистику. Ограничение доступа к этим ручкам — на стороне API.
3. **`GetServerData` отдаёт пароль** любому участнику ивента. Пароль лежит в БД открытым
   текстом.
4. **`server_ip` — это строка, а не UUID.** Колонка `TEXT`, валидация только на непустоту и
   длину: формат адреса задаёт vps-сервис, и разбирать его здесь — значит рисковать отказом
   на валидном адресе. Адрес обрезается по краям в обоих сообщениях, иначе сверка пары в
   `vps.deployed` спотыкалась бы на пробелах.
5. **Сайд-лидеры не могут выйти из ивента** и не могут быть убраны из состава: они обязаны
   играть каждую игру и попадают в составы всех своих команд сразу при создании ивента с
   ролью `squad_leader`.
6. **Лимит 50 на команду включает сайд-лидера**, то есть свободных мест 49.
7. **Роли только в `team_members`.** У участия в ивенте (`users`) роли нет: один человек
   может быть сквадным в первой игре и рядовым во второй. `SetRole` принимает `team_id`,
   а не `event_id`.
8. **`server.rent` публикуется один раз и только пока ивент `confirmed`.** Если сервер уже
   куплен (статус `purchased` и дальше), повторный заказ не уйдёт — иначе арендовали бы
   второй сервер. Отсюда обязательный порядок: сначала наш `server.rent`, потом покупка.
9. **Порядок `vps.purchased` → `vps.deployed` обязателен.** `vps.deployed` без покупки
   отклоняется: сервису нечего сверять.
10. **`deployed_at` — наши часы, не время vps-сервиса.** В сообщении времени нет; 15 минут
   считаются от момента получения. Момент хранится в БД, поэтому рестарт не обнуляет
   отсчёт.
11. **При досрочном 2:0 несыгранная игра остаётся в статусе `pending`.** Это не забытое
    состояние: стартовать её нельзя, потому что ивент уже `finished`.
12. **Статистика перезаписывается, а не суммируется.** Повторный `AddTeamMemberStats` на
    того же игрока — это способ исправить числа. `total_*` команды каждый раз считается
    заново как сумма по составу.
13. **`TIMESTAMP` без таймзоны.** Все колонки времени — `TIMESTAMP`, и пишется в них
    `time.Now()`. Пока контейнеры в UTC, всё сходится; при смене TZ времена поедут.
    Перевод на `TIMESTAMPTZ` — отдельная задача.
14. **NULL против нулевого времени.** `time_finish`, `server_deployed_at`, `ally_ready_at`,
    `enemy_ready_at`, `team.time_start/time_finish` в БД NULL, пока события не произошло, и
    читаются через указатель. В домене это нулевой `time.Time`, в protobuf — отсутствующее
    поле. Не пишите туда нулевое время: `0001-01-01` неотличим от «ещё не случилось» только
    на вид.
15. **proto3 не печатает значения по умолчанию.** В JSON от `grpcurl` не будет ни
    `"enemyReady": false`, ни нулевых чисел, ни пустых строк. В тестах и скриптах пишите
    `jq -r '.event.enemyReady // false'`, иначе получите `null`.
16. **Таймеры живут в памяти одного процесса.** Данные в БД останутся согласованными и при
    нескольких инстансах, но таймеры сработают в каждом: подтверждение и старт пройдут один
    раз (защищают переходы статусов), а вот `server.rent` может уйти дважды. **Пока держите
    один инстанс**; для масштабирования нужен один «планировщик» (leader election или
    advisory lock).
17. **Публикация после коммита** означает, что при недоступной Kafka состояние в БД уже
    изменено, а вызывающий получит ошибку. Повторять запрос в этом случае нельзя —
    большинство ручек ответят `AlreadyExists` или `FailedPrecondition`.
18. **Мьютекс держится и во время публикации.** Если Kafka тормозит, другие запросы по
    этому же ивенту ждут (до 30 секунд). По разным ивентам — не ждут.
19. **Пока сервис не в проде — миграция одна и правится на месте.** Следствие: на базе, где
    версия 1 уже применена, `migrate up` ничего не сделает, и схема разойдётся с кодом
    (сервис упадёт на первом же запросе — `scanEvent` выбирает колонки, которых нет).
    Обновлять такую базу нужно через `make db-reset`. После выхода в прод так делать нельзя:
    изменения схемы оформляются как `000002_*.up.sql` / `.down.sql` и далее по порядку.
20. **Порог `six_clan_members` задан в двух местах** — в SQL (`count >= 5` без самого
    игрока) и в сервисе (`< 6` всего). Меняете один — меняйте второй.
21. **Индексов под частые выборки нет:** `events` по `user_create_id` и `name`, `users` по
    `user_id`. На нынешних объёмах незаметно.

## Известные ограничения

Осознанный технический долг — если берётесь за что-то из списка, начните с обсуждения.

- **Нет transactional outbox.** Публикация после коммита может не состояться; событие
  потеряется, состояние в БД останется. Правильное решение — таблица outbox и отдельный
  публикатор.
- **Нет проверки прав на игровых ручках** (пункты 1–3 выше).
- **Нет баланса сторон.** `MinPlayersRequired` считает всех участников: 80 человек могут
  оказаться на одной стороне, и ивент подтвердится. Минимум по стороне не задан.
- **Игра стартует независимо от наполненности составов** — в команде может быть только
  сайд-лидер.
- **Одна игра не может закончиться вничью:** `team_winner_id` обязателен. Ничья есть только
  на уровне серии.
- **Тайминги — константы в коде.** Чтобы прогнать e2e, приходится собирать копию с другими
  значениями. Стоит вынести их в переменные окружения.
- **`TIMESTAMP` без таймзоны** и пароль сервера открытым текстом (пункты 12 и 3).
- **Таймеры не переживают горизонтальное масштабирование** (пункт 15).

## Как добавить ручку или сообщение

### Новая gRPC-ручка

1. `internal/core/proto/event.proto`: добавить `rpc`, `*Request`, `*Response`; `make proto`.
2. `internal/layers/service/port.go`: добавить метод в `EventService` с комментарием, что он
   делает и в каких статусах разрешён.
3. `internal/layers/service/service.go`: реализовать по общей схеме:
   валидация входа → мьютекс ивента → `WithTx` (первым делом `lockEventRow`, потом проверки
   по прочитанной строке и изменения) → публикация в Kafka после коммита.
4. Ошибки размечать конструкторами из `domain` (`InvalidArgument`, `NotFound`,
   `PermissionDenied`, `FailedPrecondition`, `AlreadyExists`) — от этого зависит gRPC-код.
5. `internal/layers/transport/grpc.go`: хендлер на 5 строк — вызвать сервис, при ошибке
   `return nil, fail("MethodName", err)`.
6. Тесты: успешный путь, все отказы с проверкой категории, сбой репозитория (через
   `repo.fail`) с проверкой отката, сбой публикации.
7. Если ручка меняет состояние — добавить в `e2e_test.sh`.

### Новое исходящее событие

1. Метод в `internal/core/kafka/producer.go` (JSON с полем `type`, ключ — `event_id` или
   `team_id`).
2. Тот же метод в интерфейс `EventProducer` в `port.go` и в `fakeProducer` в
   `fakes_test.go` (там он просто пишет `type` в список).
3. Вызвать из сервиса **после** коммита. Обновить таблицу событий в этом README.

### Новое входящее сообщение

1. Поле в `vpsMessage` и ветка в `switch` в `internal/layers/transport/kafka.go`.
2. Метод в `EventService` + реализация в сервисе. Обязательно продумать **идемпотентность**:
   Kafka доставляет минимум один раз, повтор не должен менять состояние второй раз.
3. Решить, какая ошибка означает «повтори» (`Internal`/`Unavailable`/`Aborted`), а какая —
   «пропусти» (всё остальное): от этого зависит, заблокирует ли сообщение партицию.
4. Если нужен новый топик — добавить его в `kafka-init` в `docker-compose.yml` и в
   переменные окружения.
